# Versions and commit SHA pins

[Documentation home](../README.md) · [Helper catalog](helpers/README.md)

All nine Actions and both reusable workflows share the repository's **v2.5.0** version. The source on a development branch prepares that version; use it in production after the corresponding GitHub release has completed successfully.

## Choose a reference

An exact version is convenient for developer workflows:

```yaml
- uses: alconite-inc/alconite-actions/node-ci@v2.5.0
```

For company workflows, copy the full 40-character commit SHA from the release's **release-pins.md** asset and retain its version comment. Each release publishes both the readable examples and **release-pins.json**, a machine-readable mapping of all entry points to that same commit. These are generated by resolving the actual Git tag, including annotated tags, rather than by copying a branch SHA.

- [v2.5.0 release and SHA examples](https://github.com/alconite-inc/alconite-actions/releases/tag/v2.5.0)
- [Download release-pins.md](https://github.com/alconite-inc/alconite-actions/releases/download/v2.5.0/release-pins.md)
- [Download release-pins.json](https://github.com/alconite-inc/alconite-actions/releases/download/v2.5.0/release-pins.json)

These links become available after publication. An Action commit SHA is a Git identifier; a Sentinel image digest starts with `sha256:` and identifies registry content. They are different pins. The release notes provide the Sentinel digest separately.

Exact SemVer tags are the release contract and must never be moved after publication. A full SHA also protects a caller against a tag being moved. Avoid branch references for production. Repository-wide moving major/minor Action tags are not part of the v2 release contract; the container's `2`, `2.5`, and `latest` aliases have separate rules.

## Verify and copy pins

Fetch the selected tag into a clean clone and resolve the underlying commit:

```bash
git clone https://github.com/alconite-inc/alconite-actions.git
cd alconite-actions
git fetch origin tag v2.5.0
git rev-parse 'refs/tags/v2.5.0^{commit}'
git switch --detach v2.5.0
node scripts/generate-release-pins.mjs v2.5.0 /tmp/alconite-release-pins
cat /tmp/alconite-release-pins/release-pins.md
```

Compare the resolved commit with the published mapping before copying a SHA example. GitHub requires a literal `uses:` reference: do not put a shell variable, workflow expression, or shortened SHA there. Keep the component path when replacing a version: the root runs Contract Guard, `/node-ci` runs Node CI, and `/.github/workflows/stack-ci.yml` selects the reusable workflow. Actions go in `steps`; reusable workflows go in `jobs.<job>.uses`.

## SHA policies and reusable workflows

Pinning a reusable workflow fixes its workflow file, but Stack CI and the Runtime Verify reusable workflow call Alconite helpers at the exact version tag internally. Organizations requiring a full SHA at **every** call should compose the individual helpers in their own workflow using the release mapping. External Actions inside the helpers already use full SHA pins. An organization enforcing an action allowlist must also permit these referenced upstream Actions; SHA pinning does not bypass that policy.

## Upgrading from v2.4

1. Review the [changelog](../CHANGELOG.md) and each helper's requirements.
2. Update every Alconite entry point to the same release version or its verified SHA.
3. For Stack CI image publication, grant `contents: read` and `packages: write`. GitHub attestation and OIDC write permissions are no longer required. Existing extra grants can be removed when no other caller step needs them.
4. If your policy requires GitHub artifact attestation, use the optional composition in the [Docker helper guide](helpers/docker-ci.md), where the caller explicitly grants the necessary permissions.
5. Run a pull request build and a trusted publication build. Private Java/Node dependency tokens are withheld on all pull requests; a private dependency build may need a separate trusted workflow.

## Maintainer release sequence

Update `package.json`, the lockfile, component identities, current examples, tests, container defaults, and the dated changelog together. Run `npm ci`, `npm audit --audit-level=high`, `npm run verify`, and `actionlint`, and commit all generated distributions. Container changes also require the image checks described in [Contributing](../CONTRIBUTING.md).

After review and merge, tag the exact reviewed release commit on `main`. Publishing that new tag starts the release workflow. It checks the tag/package match and main ancestry, verifies the distributions, and resolves the tag to generate the SHA examples. The release pins generator rejects a missing tag, a mismatched version, a different checkout, or tracked uncommitted changes. The release then publishes its image and attaches the mapping to its GitHub release notes.

The mapping is a release artifact because a commit cannot contain its own final SHA: changing documentation changes the commit. Do not amend or retag a published release to insert a hash. Each subsequent version generates its own mapping from its own tag target. If preparing a candidate locally, a local tag and generated mapping are review material until the reviewed commit is on `main` and publication succeeds.
